## 1. プロダクトコンセプト

既存SNS（X, YouTube, TikTok等）は「Influence（知名度・数）」のみを権力指標とするため、デマや陰謀論が
拡散インセンティブに乗って増幅されるという構造的バグを持つ。Rengaは、ユーザーを以下の2軸で評価する。

- **Influence（影響力）**: フォロワー数・リポスト数・インプレッション等、従来型の「数」の指標。
- **Intellect（知能スコア）**: 段階的IQテスト・ロジックチェックの実績・専門家Endorseの蓄積によって決まる「質」の指標。

この2軸のマトリクスにより、healthyな緊張関係（ゲーム性）を持つ情報空間を構築する。

## 2. エコシステム設計（4クラスタ）

| クラスタ | 軸 | 役割 |
|---|---|---|
| ① 天才インフルエンサー | 高Influence × 高Intellect | 議論のトレンドセッター |
| ② 裸の王様 | 高Influence × 低Intellect | 発言の「底」が知能バッジ非表示により露呈 |
| ③ 隠れた賢者 | 低Influence × 高Intellect | 知能バッジのブーストで下剋上が可能 |
| ④ 観客・同調レイヤー | 低Influence × 低Intellect | エンタメ消費者、ベットで参加、世論形成 |

クラスタはUI上の固定ラベルとしてではなく、`influence_percentile` と `intellect_percentile` の
組み合わせから**動的に算出**し、プロフィールの表示ロジック（バッジ表示/非表示）にのみ反映する。
ユーザーに直接「あなたは裸の王様です」等のレッテルを貼らない（劣等感の排除は要件の根幹）。

## 3. 機能要件一覧

### 3.1 メディア共有（画像・動画投稿 / YouTube連携）

Twitter(X)のように、テキストだけでなく画像・動画を手軽に共有できることを前提とする。

- **画像投稿**: カメラロール/カメラから選択し、複数枚添付可能（既存のSupabase Storage経由）。
- **動画投稿**: 撮影・選択した動画を**Mux**にアップロードし、アダプティブストリーミング（HLS）で配信。Supabase Storageには動画本体を置かず、帯域・容量消費を抑える（詳細は [system.md — Mux動画アーキテクチャ](system.md#5-mux動画アーキテクチャ)）。
- **YouTube埋め込み**: 投稿本文にYouTubeのURLが含まれる場合、フィード上でYouTube公式プレーヤーとしてインライン再生できるカード表示に自動変換する。
- **YouTubeアプリの共有シートに登場**: YouTubeアプリの「共有」から直接Rengaを共有先として選択できるようにする（Android/iOSのシェアターゲット登録）。共有された動画リンクはComposeボトムシートに自動でプリフィル（引用ポスト的に「この動画についてコメントする」導線）され、YouTube動画への論評・ロジックチェックの起点になることを狙う。

### 3.2 段階的IQテスト（Thought Power エンジン）

- **オンボーディングクイズ**: 初回登録時に3問。直感で解ける難易度。暫定Intellectランクを決定。
- **デイリーミッション**: 1日3問。クリアで TP（Thought Power）とボーナスポイントを付与。連続日数ボーナスあり。
- **ロック解除クイズ（通行料）**: 「シリアス投稿（ステーキング・ツイート）」時に1〜2問を義務化。冷却期間として機能し、荒らし・ボット投稿を抑制。

出題は正確性よりも「離脱防止」を優先し、以下を満たす：

- 1問あたり制限時間を短く設定（10〜20秒）
- 出題タイプ: 論理パズル、幾何学パズル、時事ロジック問題（陳腐化を防ぐため問題プールを定期更新）
- 正答率・回答時間・回答パターンをバックエンドに蓄積し、動的に `intellect_score` を収束させる
- 問題自体はGemini APIによる自動生成＋マルチエージェント検証パイプラインで作られる（技術詳細は [system.md — Gemini AI活用アーキテクチャ](system.md#6-gemini-ai活用アーキテクチャ)）

### 3.3 知能バッジとレイヤーフィルター

- **知能バッジ表示条件**: 上位25%のユーザーのみバッジ表示。それ未満は「無表示」（バッジなし＝一般層。マイナス表示は絶対にしない）。
- **バッジ段階**: 上位25% / 上位10% / 上位5% / 上位1% の4段階（表示色・意匠を変える）。
- **インテリジェンス・レイヤー・フィルター**: タイムライン上部にワンタップ切り替えUI。
  - 「全ユーザー」/「上位25%以上」/「上位5%のみ」
  - 選択状態はローカル保存＋アカウント同期。
- **バッジ・スコア要素のタップ詳細表示**: 知能バッジ・専門家バッジ・ステーキング表示・Influence/Intellect
  スコア等、意味の分かりにくいUI要素はすべてタップ可能にし、ボトムシートまたはダイアログで
  「何を表しているか」「どうすれば上がるか」等の説明を表示する（Instagram/Xの認証バッジタップ時の
  説明ポップアップと同様の体験）。

### 3.4 ステーキングとロジックチェック

- **ステーキング・ツイート**: 投稿時にTPを賭ける。賭け量に応じて「高知能層フィード」への露出優先度が上がる。ロック解除クイズ通過が前提。
- **ロジックチェック（下剋上バトル）**: 対象投稿に対し、挑戦者がTPを賭けて反論投稿を作成。バトルは「投稿ペア」として構造化され、一定時間（例: 24〜72時間）観客の投票・上位層のジャッジを受けて勝敗が決まる。
- **観客ベットシステム**: 一般ユーザーがバトルの勝敗にTPをベット。的中で配当＋「勝者側」のバッジ的演出（**TPは換金不可の内部ポイント**とし、賭博規制リスクを避ける）。

### 3.5 AI自動専門家発掘システム

- **サイレント・ドメイン・マッピング**: 投稿時にAI（Gemini）がテキストを解析し、専門領域ラベル（医療/自動車/歴史 等）を自動付与。ユーザー操作は不要。
- **Endorseによる裏スコア加算**: 該当分野のバッジ保持者からのEndorseにより裏の分野別スコアが加算。閾値超過で専門家バッジを実績解除として付与（プッシュ通知でサプライズ演出）。

### 3.6 デマ対策・拡散抑止

1. **無自覚な拡散のストップ**: バッジなしユーザーが未検証情報をリポストしようとすると「この情報は上位25%層の検証が完了していません」と警告。
2. **専門家と高知能による挟み撃ち**: 専門家バッジ/高Intellectユーザーがロジックチェックを起動し、科学的・論理的に反証。
3. **警告付与と拡散停止**: 上位5%による「論理破綻」認定が閾値に達した投稿には強制的に警告バッジが付与され、拡散が停止する（削除はしない＝表現の自由と両立）。
4. **良い投稿の救済**: 逆に一般層の「素朴だが核心を突く投稿」は高知能層のEndorseで即座に高知能限定タイムラインへ昇格（インテリジェンス・バックアップ）。

### 3.7 3ストライク・累積ペナルティ

| 段階 | 内容 |
|---|---|
| 1st | Intellectスコア大幅減点、賭けTP没収、プロフィールに「直近でロジック破綻を記録」ラベルを14日間表示 |
| 2nd | 知能バッジ強制剥奪、高知能タイムラインへの投稿権限を数ヶ月ロック、収益分配（将来機能）から除外 |
| 3rd | アカウントの知能データ・フォロワー・TPを完全リセット。ユーザーIDは維持するが実質再スタート |

ストライクは「上位5%ジャッジ／専門家バッジ保持者による論理破綻認定」が一定数（閾値）累積した場合に自動発火。誤爆防止のため、認定には最低人数のクォーラムと異議申し立て（Appeal）フローを設ける。

技術的な実装レベルの詳細（テーブル設計・発火条件・ロールバック処理）は [system.md — デマ対策・ストライク実装](system.md#7-デマ撲滅フローと3ストライク実装) を参照。

### 3.8 AIアシスト対策への基本方針

低知能ユーザーがLLMをゴーストライターとして使うこと自体は「情報空間の健全化」に寄与するため許容・推奨するが、
チート行為（AIによるクイズ自動回答・ロジックチェック荒らし）は防ぐ。具体的な対策（時間制限・出題形式・レートリミット等）は
[system.md — AIアシスト対策・不正検知](system.md#8-aiアシスト対策不正検知) を参照。

### 3.9 通報・コンテンツモデレーション

デマ・論理破綻への対策（3.6）とは別に、暴力的・性的・誹謗中傷的コンテンツ等への安全性対策を用意する。

- すべての投稿・動画・プロフィールに**通報ボタン**を設置。
- 画像・動画・テキストはAI（Gemini）による自動一次チェックを経て公開し、疑わしいものは公開前後に一時非表示にして人間レビューに回す。
- 通報が集中したコンテンツも同様に一時非表示＋レビューキューへ。24時間以内の一次対応を運用目標とする。

技術的な実装詳細は [system.md — コンテンツモデレーション・Trust & Safety](system.md#13-コンテンツモデレーショントrust--safety) を参照。

### 3.10 プロフィール詳細設定

InstagramやXのプロフィール編集画面と同等に、自分のプロフィールをより詳細にカスタマイズできるようにする。

- **編集可能項目**: アバター画像（既存の`image_picker`でカメラロールから選択しSupabase Storageへ
  アップロード、`profiles.avatar_url`を更新）、display_name、bio、**website_url**（外部リンク1件）、
  **location**（自由入力のテキスト、位置情報の実測は行わない）。
- **編集UX**: Profile画面自体は常に読み取り専用ビューとして表示し、「編集」ボタンをタップした時のみ
  上記項目をまとめて編集できる専用ボトムシートを開く（画面本体に編集フォームを埋め込まない）。
  保存もボトムシート内で完結させる。**キャンセル操作はボトムシート内に専用の「キャンセル」ボタンを
  置かず、シート自体を閉じる（下スワイプ／シート外タップ／端末の戻る操作）ことでキャンセル扱いとする**
  （5章のデザインシステム方針・全ボトムシート共通のルールに準拠）。
- **読み取り専用の統計表示**: username、TP残高、ストライク状態、知能バッジ段階は編集不可
  （不正操作防止のため、いずれもサーバー側算出値）。
- **Influence/Intellectスコアの表示形式**: `influence_score` / `intellect_score` は元々ログスケールの
  合成値で小数点以下が長く人間に読みにくいため、プロフィール画面では**0〜5段階に正規化した表示値**
  （`(percentile / 100) * 5` を小数第1位に丸めた値、例: 「4.2 / 5」）を主表示とする。生の
  `influence_score` / `intellect_score` はサーバー内部の算出用途に留め、UIには表示しない
  （パーセンタイルは補足情報として小さく併記してもよい）。
- **Intellect＝IQという表現の明確化**: Intellectスコアはパーセンタイルを平均100・標準偏差15の
  IQスケールに換算した数値（`lib/shared/iq_format.dart`）で主表示しているため、ラベルは
  「Intellect（IQ）」のように、それがIQ相当の指標であることが一目で分かる表記に統一する
  （バッジ・詳細説明ボトムシートも同様）。
- **平均値との比較・前日比の表示**（system.md 2章「平均値・日次推移」）: IQ表示・Influence表示の
  すぐ横に、全ユーザー平均との差分（例: IQなら「平均より+15」、Influenceならパーセンタイル差で
  「平均より+8」）を小さく併記する。Influenceはさらに前日からの変化（例: 「前日比 +3」）も表示する。
  いずれも `score_stats`（全ユーザー平均のキャッシュ）・`user_score_history`（日次スナップショット）
  から取得する（system.md 1章・2章）。
- **推移グラフ**: IQ表示部分、Influence表示部分はそれぞれタップ可能にし、タップすると
  `user_score_history` の時系列データを折れ線グラフ（`fl_chart`）で表示するボトムシートを開く。
  グラフには全ユーザー平均（`score_stats`）を横線（基準線）として重ねて表示し、自分の推移が
  平均に対してどう変化しているかを視覚的に把握できるようにする。
- **他ユーザーのプロフィール閲覧**: フィード・コメント・バトル等でアバターやユーザー名をタップすると、
  そのユーザーのプロフィールを同じレイアウトの読み取り専用ビューで閲覧できる（`/profile/:userId`
  ルート）。自分自身の場合のみ「編集」ボタン・TP残高・ストライク状態等の自分専用UIを表示し、
  他人のプロフィールでは編集ボタン・ログアウトボタンを非表示にする。
- **ログアウト導線の一本化**: ログアウトボタンはProfile画面には置かず、Settings画面のアカウント
  セクションのみに配置する（3.11節）。
- **バッジ・スコアのタップ詳細**（3.3節）: プロフィール上のバッジ・スコア表示（知能バッジ、TP残高
  チップを含む）もタップで詳細説明のボトムシートを表示する。TP残高チップタップ時は「TP
  （Thought Power）とは何か」「クイズ正解・デイリーミッションでの獲得方法」「ステーキング投稿・
  ロジックチェックでの用途」を平易に説明する（3.2節・3.4節の要約）。
- 技術的なテーブル拡張（`profiles.website_url` / `profiles.location`列の追加）は
  [system.md 1章](system.md#1-データモデルsupabase--postgres) を参照。

### 3.11 Settings（設定）画面

Profile画面の歯車アイコンから遷移する専用画面。Instagram/Xの設定画面同様、以下をセクション分けして提供する。

- **画面の役割分離**: Settings画面自体は**設定項目への遷移リストのみ**を表示し、実際の値の変更UI
  （フォーム入力・選択肢の確定操作）はSettings画面には埋め込まない。各行をタップすると専用のサブ
  ページ（`Navigator.push`／go_routerの子ルート）に遷移し、そのサブページ内で変更・保存を完結させる。
  例外は「通知のON/OFF」のようなその場で完結する単純なトグルのみで、これは従来どおりSettings画面内
  の`SwitchListTile`で直接切り替えてよい。
- **アカウント**: ログイン中のメールアドレス表示（読み取り専用）に加え、以下のサブページへの行を配置:
  - **プロフィール編集**: 3.10節のプロフィール編集項目（アバター・display_name・bio・website_url・
    location）を編集する専用ページ。Profile画面の「編集」ボタンから開くボトムシートとは別に、
    Settings経由でも同じ編集内容に到達できる導線を用意する（実装上は同じ編集ロジック/フォームを
    再利用してよい）。
  - **パスワード変更**: 現在のパスワード確認は求めず（Supabase Authのセッションで認証済みのため）、
    新パスワード入力＋確認入力の専用ページ。`supabase.auth.updateUser(password: ...)`で更新。
  - **アカウント削除**: 影響範囲（投稿・フォロー・TP等が全て失われる旨）を明示した確認ページ。
    実行にはメール再認証または明示的なテキスト入力確認（例: ユーザー名の再入力）を必須とし、誤操作
    による削除を防ぐ。削除処理はクライアントから直接`auth.users`を消せないため、Supabase Edge
    Function（例: `delete_account`）でサービスロールキーを用いて`auth.users`削除（`profiles`は
    `on delete cascade`で連動削除）を行う。
  - **ログアウト**: 引き続きこのセクションにボタンとして配置する（Profile画面からは撤去、3.10節）。
- **通知**: プッシュ通知の受け取りON/OFF（ONの場合のみ`device_tokens`へFCMトークンを登録し続け、
  OFFにした場合は端末側でのトークン登録解除・送信停止の意思表示として扱う。詳細な通知種別ごとの
  粒度設定はPhase2以降）。単純なON/OFFトグルのため画面内の`SwitchListTile`のまま直接切り替える。
- **表示設定**: レイヤーフィルターの既定値（3.3節の設定と同じ値を共有）、ライト/ダーク/端末設定に
  従うのテーマ選択。それぞれ専用のサブページに遷移し、選択肢一覧から1つを選ぶと即座に確定して前の
  画面へ戻る（Settings画面内にその場でボトムシートを開く従来方式は廃止し、他の項目と同様にページ
  遷移に統一する）。
- **表示言語**: 英語/日本語の切り替え（5章の多言語対応方針に基づく。端末言語追従が既定）。表示設定
  と同様に専用サブページで選択する。
- **ボトムシートを使う場合のキャンセル操作**: このセクションに限らずアプリ全体の方針として、
  ボトムシートに明示的な「キャンセル」ボタンは置かない。シートを閉じる操作（下スワイプ／シート外
  タップ／戻る操作）自体がキャンセルとして機能する（5章参照）。
- **ボトムシート・全画面ビューアの表示範囲**: ボトムシート（`showModalBottomSheet`）や
  写真・動画の全画面ビューア（`FullscreenMediaViewer`のpush遷移）は、必ず`useRootNavigator: true`
  （全画面push時は`Navigator.of(context, rootNavigator: true)`）でルートNavigator上に表示する。
  ボトムナビゲーションの各タブは`StatefulShellRoute`のブランチごとに独立したネストNavigatorを
  持つため、これを指定しないとシート/ビューアの表示範囲がタブのコンテンツ領域に限定され、
  画面下部にボトムナビゲーションバーが透けて見えてしまう。
- 将来的にプライバシー設定・ブロックリスト等をここに追加していく想定（Phase2以降）。

### 3.12 基本エンゲージメント機能（いいね・コメント・リポスト・共有）

Instagram/X同様、投稿ごとに以下の基本的なエンゲージメント手段を提供する。3.4節の「ステーキング/ロジックチェック」とは別レイヤーの、シンプルな反応・拡散手段として位置づける。

- **アクションバーの表示形式**: いいね・コメント・リポストはInstagram同様、**テキストラベルを持たず
  アイコンのみ**で表示する。件数（カウンター）はアイコンの右側に表示し、**件数が0の場合は数字自体を
  表示しない**（アイコンのみ）。共有ボタンはカウンターを持たないためアイコンのみで常時表示。
- **いいね**: 投稿へのワンタップの好意表示。トグル式（再タップで取り消し）。
- **コメント**: 投稿に対する短文コメントのスレッド。コメントボタンをタップするとボトムシートで
  コメント一覧と投稿フォームを表示する（新規画面への遷移はしない）。
  - **表示要素**: 各コメントに投稿者のアバター画像と、投稿からの経過時間（相対時間表示、例:
    「3分前」「2時間前」「3日前」。一定期間を超えたら日付表示にフォールバック）を表示する。
  - **返信（スレッド化）**: 各コメントに「返信」導線を設け、対象コメントへの返信を投稿できる
    （`comments.parent_comment_id`で1階層のスレッドとして親コメントに紐づく。返信一覧は親コメント
    の下にインデントして表示）。
  - **返信への画像・動画添付**: コメント本体だけでなく返信にも、投稿と同様に画像（複数可）・動画
    （Mux経由）を添付できる（3.1節のメディア共有の仕組みを流用）。
- **リポスト（X風の2択ボトムシート）**: アクションバーのリポストアイコンをタップすると、即座にトグルせず
  X(Twitter)同様の選択肢をボトムシートで提示する。
  - **リポスト**: 既存のリポスト機構（3.6節「デマ対策」の警告フローと共通の`reposts`テーブル）への
    無条件の再共有（引用なし）。トグル式で、既にリポスト済みの場合はボトムシートの1つ目の選択肢が
    「リポストを取り消す」に変わり、再選択で取り消せる（既存挙動を維持）。
  - **引用リポスト**: コメント付きで再共有する。選択すると投稿作成シート（3.1節の投稿作成UIと共通）が
    引用元投稿の要約プレビュー（アバター・ユーザー名・本文冒頭・メディアサムネイル等のミニカード）付きで
    開き、コメントを書いて投稿すると通常の投稿と同様に新規投稿が作成される
    （`posts.quoted_post_id`に引用元投稿のIDをセット。system.md 1章参照）。単純リポストと異なりトグルでは
    なく、通常投稿と同じく複数回作成できる。
  - フィード・投稿詳細のいずれでも、`quoted_post_id`が設定された投稿には引用元投稿の要約ミニカードを
    インライン表示する。ミニカードをタップすると、一覧から投稿をタップした場合と同じ挙動で引用元投稿の
    詳細画面（3.12節冒頭のスレッド表示）へ遷移する。
- **共有**: OS標準の共有シート（`share_plus`）を呼び出し、投稿本文・メディアURLを他アプリへ共有できるようにする。
- **フィード投稿カードのタップ範囲**: 一覧（Feed/Discover）の投稿カードは、本文テキスト部分に限らず
  カード全体（余白部分・アクションバーの隙間等）のタップで投稿詳細（3.12節冒頭のスレッド表示）へ
  遷移する。ただし以下は個別のタップ先を持つため、カード全体タップの対象から除外する（子要素が
  自身のタップハンドラを優先し、親のカードタップと二重発火しない）。
  - メディアプレビュー（画像・動画・YouTube埋め込み）→ 全画面ビューア（3.13節）
  - **ユーザー情報表示部**（アバター・ユーザー名・知能バッジ）→ 一帯全体を単一のタップ領域とし、
    どこを押しても該当ユーザーのプロフィールへ遷移する。知能バッジ自体はこの文脈では
    バッジ詳細シート（3.3節）を開かず、ユーザー情報表示部の一部としてプロフィール遷移に委ねる
    （バッジ詳細シートはプロフィール画面等、投稿カード以外の文脈でのみ機能する）。
  - アクションバーの各ボタン（いいね・コメント・リポスト・共有）→ それぞれの既存アクション（リポストは
    上記のボトムシート表示）
  - 引用リポストの引用元ミニカード → 引用元投稿の詳細画面

技術的な実装詳細（テーブル設計・RLS、コメントのスレッド化・メディア添付のための列拡張）は [system.md 1章](system.md#1-データモデルsupabase--postgres) を参照。

### 3.13 メディア表示・再生UX（画像複数枚・動画自動再生・全画面表示）

タイムライン上のメディア体験をInstagram/TikTok的な「軽量プレビュー→タップで没入」の体験に揃える。

- **画像の複数枚投稿**: 1投稿に複数枚の画像を添付でき（既存の`posts.media_urls`配列をそのまま活用）、
  フィード上は横スクロール（`PageView`）で閲覧する。画像枠の下部中央に**ドットインジケーター**を
  配置し、総枚数と現在の閲覧位置を示す。全画面表示時も同じ横スクロール＋ドットのUXを踏襲する。
- **動画の自動再生（スクロールイン）**: フィードをスクロールし動画が画面内に一定割合入ったタイミングで
  **自動的にミュート再生を開始**し、画面外に出たら自動停止する（バックグラウンド通信・電池消費を
  抑えるため、画面内にある動画のみアクティブにする）。フィード内の自動再生は帯域・処理負荷を抑える
  ため**軽量なプレビュー品質**（低ビットレート/縮小サムネイルベースのループ、または低解像度HLS
  レンディション）で行い、ユーザーがタップして全画面に入った時点でフル品質のストリームに切り替える
  （「サムネイル再生」に近い体験。技術詳細は [system.md — Mux動画アーキテクチャ](system.md#5-mux動画アーキテクチャ)）。
- **動画プログレスバーの位置・操作性**: 再生時間バーは動画枠の中央に重ねず、**枠の下部（下端）**に
  配置する。バー上には現在の再生位置を示す**ドラッグ可能なつまみ（シークハンドル）**を設け、つまみを
  ドラッグすることで再生タイミングを任意の位置に変更できる。
  - **全画面表示ボタン**: 動画枠内に全画面表示への切り替えボタンを常設する。
- **タップで全画面表示**: フィード上の画像・動画をタップすると、共通の**全画面メディアビューア**が
  開く。
  - 動画は全画面表示時にフル品質のHLSストリームへ切り替え、下部バー＋シークつまみで再生位置を操作
    できる（フィード内表示と同じ操作系を維持）。
  - 複数画像投稿は全画面表示でも横スクロール＋下部ドットインジケーターを維持する。
  - 全画面ビューアは下スワイプ等の操作で閉じられる（3.11節と同様、専用の「閉じる」ボタンだけに
    頼らない直感的な操作を優先しつつ、明示的な閉じるアイコンも併設してよい）。

### 3.14 クイズ回答結果フィードバック

- 3.2節のオンボーディング/デイリー/ロック解除クイズいずれも、選択肢を1つ回答したら即座に
  「正解」「不正解」を判定結果として画面に表示する（不正解の場合は正解の選択肢も併せて示す）。
- 正誤フィードバックと「次へ」ボタンは、設問画面を別ページへ遷移させず、設問画面の上に重ねる
  **オーバーレイパネル**として表示する（別Scaffold/別ルートには遷移しない）。パネルはボトム
  シート相当の見た目（下端から立ち上がる角丸パネル＋背後の半透明スクリム）とし、5章の方針に
  沿ってフェード＋下からのスライドで出現・消失させる。設問の選択肢は表示中タップ不可にする。
- 結果表示（オーバーレイパネル）には「次へ」ボタンを設け、タップすると次の設問（最後の設問の
  場合は結果サマリー画面）へ進む。自動で次に進めず、ユーザー操作で明示的に進む。
  最後の設問で「結果を見る」をタップした際は、集計処理（デイリーミッションのTP付与RPC等）が
  完了するまでオーバーレイを表示し続け（ボタンはローディング状態にする）、処理完了と同時に
  結果サマリー画面へ切り替える。処理完了前にフィードバック表示を消してしまうと、設問画面へ
  一瞬戻ったように見えて結果が表示されないよう見える不具合になるため、状態更新は
  「フィードバック非表示」と「結果サマリー表示」を同一の更新にまとめて行う。

### 3.15 デイリーミッションの受験可否・クールダウン表示

- 3.2節「デイリーミッション: 1日3問」は1日1回のみ受験可能（`award_daily_completion_tp` RPCが
  UTC日付ベースで多重付与を防止する）。本日分を既に完了しているユーザーがデイリークイズの
  設問画面に入れてしまうと、3問回答後にRPCがエラー（`P0001`）を返して行き止まりになる体験
  になってしまうため、**そもそもクイズ画面へ遷移させない**。
- フィード画面等のデイリークイズ導線ボタンは、本日分完了済みの場合は非活性化（タップ不可）にし、
  ボタンの隣に「次に挑戦できるまで」の残り時間をカウントダウン表示する（UTC 0時にリセット）。

### 3.16 Discoverのキーワード検索

- 3.5節のDiscover画面は、ドメイン（産業大分類）による絞り込みに加えて、キーワードによる
  投稿本文の検索を提供する。検索ボックスに入力したキーワードを含む投稿本文を、選択中の
  ドメインでの絞り込みと組み合わせて（AND条件で）一覧表示する。キーワード未入力時は従来通り
  ドメイン絞り込みのみの一覧を表示する。

### 3.17 ダイレクトメッセージ（DM）

Instagram/X同様の1対1DM機能。グループDMはスコープ外（Phase2以降で検討）。

- **開始導線**: 自分以外のユーザーのプロフィール画面に「メッセージ」ボタンを設置し、タップで
  そのユーザーとの会話画面を開く（会話が存在しなければ初回送信時に暗黙的に作成する）。
- **送信できるコンテンツ**: テキストメッセージ、画像（複数不可・1メッセージ1枚）、動画
  （3.1節のMux連携を流用）。
- **リアルタイム反映**: Supabase Realtimeを使い、会話画面を開いている間は相手の新着メッセージが
  ポーリングなしで即座に表示される。
- **DM一覧画面**: 会話ごとに相手のアバター・直近メッセージのプレビュー（テキストは冒頭、画像/動画
  は「画像を送信しました」等のラベル）・送信時刻・未読バッジを表示する。新着があれば一覧も
  リアルタイムで更新される。
- **既読機能**: 会話画面を開いた時点で、相手からの未読メッセージを既読にする。既読状態は
  相手の送信メッセージ側に「既読」表示として反映する。
- **通知**: 相手がアプリを開いていない/該当の会話画面を見ていない間に新規メッセージを受信した
  場合、プッシュ通知（FCM、design/system.md 8章参照）で知らせる。
- **ブロック機能**: 会話相手をブロックすると、以後そのユーザーからのメッセージ送信を拒否する
  （ブロックした側にはブロック中である旨を表示し、解除も可能にする）。ブロックされた側には
  相手が読めなくなった旨を明示的には通知しない（3.9節の通報対応と同様の方針）。
- **削除機能**: 会話単位で「削除」すると、自分の一覧からその会話が非表示になる（相手側には
  影響しない。いわゆる自分側のみの論理削除）。

技術的な実装詳細（テーブル設計・RLS・Realtimeチャンネル構成）は
[system.md 15章「ダイレクトメッセージ」](system.md#15-ダイレクトメッセージ)を参照。

## 4. 情報アーキテクチャ / 画面構成

InstagramやX(Twitter)のモバイルアプリと同じ「ボトムナビゲーション＋タブ」を基本構造に採用する
（配色・見た目の方針は5章を参照）。全画面をスマートフォン縦持ちでの利用を前提に最適化する。

```
[Splash] → ([Complete Profile: Googleサインイン新規登録時のみ]) → [Onboarding: 3問クイズ] → [Home（ボトムナビゲーション）]

Home（ボトムナビゲーション、5タブ）
├── Feed（タイムライン）
│   ├── レイヤーフィルター（全ユーザー / 上位25% / 上位5%）をInstagramのストーリー欄のように上部に固定
│   └── AppBarの投稿ボタンから[Compose](投稿作成: 通常 / ステーキング投稿の切替、画像・動画添付、
│       YouTubeリンク自動プレビュー)をモーダルボトムシートとして開く（3.10節のProfile編集シートと
│       同じ`showModalBottomSheet`パターン。専用タブ・別画面は持たない）
├── Discover（専門家発掘・ドメイン別ランキング。Instagramの「検索・発見」タブに相当）
├── Messages（DM一覧。個別会話画面のみフルスクリーンでpush）
├── Battle（ロジックチェック一覧・進行中バトル・ベット）
└── Profile（Influence/Intellectレーダー、バッジ、TP残高、ストライク状態。詳細は3.10節）

各タブ内はX/Instagram同様にネストしたスタック遷移（一覧→詳細）を持つ
（例: Feed内の投稿タップ→詳細、Discover内のユーザータップ→プロフィール）。

実装上、Messages（DM一覧）もFeed/Discover/Battle/Profileと同じ`StatefulShellRoute`のブランチとして
扱われ、タブ切替はページ遷移なしで即時に行われる（他タブと同一のIndexedStack挙動）。
DM個別会話画面のみ、一覧タブ内からフルスクリーンでpushされる別画面のままとする。

付随画面（ボトムナビゲーションの外、モーダル/プッシュ遷移）
- Complete Profile（Googleサインインで新規登録し、username等のプロフィール情報が未入力のユーザーのみ、
  ログイン直後に強制表示。サインアップ画面のusername入力フォームと同一UIを再利用し、入力・保存完了で
  ホームへ進める。設計詳細はdesign/system.md 3章「Auth」参照）
- Daily Mission（デイリークイズ）モーダル
- Lock Quiz（ステーキング投稿前の通行料クイズ）モーダル
- Battle Detail（投稿ペア比較 + 投票 + ベットUI）
- Notification（Endorse獲得、バッジ実績解除、ストライク通知。Instagramの「いいね」欄的なアイコンから遷移）
- Settings（Profile画面の歯車アイコンから遷移。詳細は3.11節）
```

- **ボトムナビゲーションのラベル表示**: Instagram/X同様、選択中のタブのみアイコン下にラベルを表示し、
  非選択タブはアイコンのみとする。一方、AppBar上の通知・デイリークイズ等の「単発アクションボタン」
  （タブではなくその場でモーダル/別画面へ遷移するだけのアイコンボタン）はラベルを表示せず、
  アイコン＋ツールチップのみでよい。
- **ページ遷移・マイクロインタラクションのアニメーション**: 画面遷移（プッシュ/ポップ）に
  Instagram/X標準相当のフェード＋わずかなスライドトランジションを適用する。バッジ実績解除・
  バトル結果発表などの「儀式的な瞬間」は5章の方針通り専用アニメーションを使う。ボトムナビの
  選択状態切り替え・いいね等のタップ時にも軽いアニメーション（アイコンのスケール/色の遷移等）を
  つける。

## 5. デザインシステム方針・多言語対応

InstagramやX(Twitter)の公式アプリに近い、見慣れた・使い方に迷わないモバイルUIを踏襲する方針に転換する
（旧方針だった「My BMW App的な作り込まれた独自UI」は撤回。学習コストの低さとスマホでの片手操作の
最適化を優先する）。

- **画面構造はボトムナビゲーション＋タブが基本**（4章参照）。各タブ内はスタック型のプッシュ遷移
  （一覧→詳細）とし、iOS/Androidそれぞれのネイティブに近いスワイプバック・戻る挙動を尊重する。
- **ウィジェットはMaterial 3ベースを土台にしつつ、配色・形状をX/Instagram寄りにカスタムする**:
  リッチな独自Paintウィジェットを大量には作り込まず、`Theme`（`ColorScheme`/`TextTheme`/
  各コンポーネントテーマ）のカスタマイズと標準ウィジェットの組み合わせで「Instagram/Twitterらしさ」
  を再現する（実装コストと保守性を優先）。
- **カラーパレット**:
  - ライトモード基調はInstagram型（背景は白〜オフホワイト、テキストは黒に近いグレー、
    アクセントに単色の鮮やかな青系）。
  - ダークモードはX(Twitter)型（背景は黒〜ダークネイビー、テキストは白、アクセントは同系の青）。
  - Influence/Intellectの2軸を象徴する配色（Influence=warm系、Intellect=cool系）は、
    背景やナビゲーション全体には使わず、バッジ・スコア表示・グラフ等のアクセント要素に限定して使う
    （UI全体のトーンはあくまでX/Instagramの落ち着いた配色を優先する）。
- **タイポグラフィ**: 独自フォントの作り込みは行わず、プラットフォーム標準に近いシステムフォント
  （英語のデフォルト・日本語の両方で可読性の高いサンセリフ）を採用する。
- **モーション**: X/Instagram標準相当の控えめなトランジション（画面遷移・いいね等のマイクロ
  インタラクション）を基本とし、バッジ実績解除・バトル結果発表など「儀式的な瞬間」のみ`Hero`や
  `Rive`/`Lottie`等の専用アニメーションを投入する。
- **カード/リストデザイン**: Instagram/Xを参考に「アバター＋名前＋バッジ」「本文」「メディア」
  「アクションバー（いいね・コメント・リポスト相当）」のシンプルな縦積みカード構成。知能バッジ・
  専門家バッジ・ステーキング表示など独自要素はアクセントとして自然に馴染ませる。アクションバーは
  ラベルを持たずアイコン＋件数（0件時は数字非表示）のみとする（3.12節）。
- **ボトムシートのキャンセル操作（アプリ全体共通ルール）**: `showModalBottomSheet`で開くあらゆる
  ボトムシート（プロフィール編集・コメント・バッジ/スコア説明・設定の選択肢等）は、専用の
  「キャンセル」ボタンを配置しない。下スワイプ／シート外タップ／端末の戻る操作でシートを閉じる
  ことそのものをキャンセルとして扱う。保存・確定などの能動的な操作のみ明示的なボタンとして残す。
- **ライト/ダークモード両対応**: 既定はシステム設定に追従し、上記の配色方針でライト（Instagram型）・
  ダーク（X型）の両方を用意する。
- **コンポーネントライブラリ化**: `packages/renga_ui` としてデザインシステムをパッケージ分離し、
  Widgetbook等でカタログ化する方針自体は維持する。

### 多言語対応（i18n）

- **デフォルト言語は英語（en）**。日本語（ja）を追加ロケールとして提供する。将来的な多言語展開を見据え、文言はハードコードせずすべてローカライズリソースで管理する。
- 端末ロケールが未対応言語の場合は英語にフォールバックする。
- クイズ問題・AI生成コンテンツ（ドメインラベル等）も英語優先で設計し、日本語は追加生成データとして持つ。
- ストア掲載情報も英語を主言語として作成し、日本語版は追加ローカライズとして用意する。
- 技術的な実装方法（ARBファイル、gen-l10n等）は [system.md — Flutterアプリ構成](system.md#9-flutterアプリ構成アーキテクチャ) を参照。

## 6. マネタイズ（AdMob広告）

Google AdMobを用いて広告収益化を組み込む。ユーザー体験を損なわないよう、洗練されたUIの中で広告枠が浮かないよう配置する。現時点でサブスクリプション等の課金機能はスコープ外とし、広告収益のみをマネタイズ手段とする。

| フォーマット | 配置 |
|---|---|
| ネイティブ広告（Native Ad） | フィードのタイムライン中に一定間隔（例: 投稿10件ごと）で自然に差し込む。広告であることが分かるラベルは明示（Playストア/AdMobポリシー準拠のため必須） |
| バナー広告 | Discover画面下部などの補助的な位置に控えめに配置（MVPでは任意） |
| インタースティシャル広告 | バトル結果発表後など、区切りの良いタイミングで頻度制限付きで表示 |
| リワード広告（任意・将来拡張） | TPを広告視聴で追加取得できるオプション（換金不可ポイントの範囲に留める） |

- 広告ユニットIDはハードコードせず、Firebase Remote Configから配信し、緊急停止（`ads_enabled` フラグ）を可能にする。
- 高知能限定タイムライン等、プレミアム感を出したい体験では広告非表示にする設計も将来検討可能（サブスクリプションの布石）。
- セットアップ手順（AdMobコンソール操作、SDK組み込み等）は [system.md — マネタイズ実装](system.md#10-マネタイズadmob実装) を参照。

追加ローカライズとして提供する。

### アプリアイコン

Renga（連歌）のブランドコンセプトに沿い、「連なる句／連なる知性」を象徴するモチーフとして、2つの輪が交差するマーク（Influenceの暖色〜Intellectの寒色のグラデーション背景に、白抜きのインターロックする2つのリング）を採用。

**仮アイコンを生成済み**（本番ブランディング確定前の暫定版。差し替え前提）:

- `assets/icon/renga_icon_background_1024.png` / `renga_icon_foreground_1024.png` — Android Adaptive Icon 背景/前景レイヤー

### ストア掲載情報

- **既定言語**: English (en-US)。日本語 (ja-JP) を追加ローカライズとして登録。

- **短い説明**（EN）: 例）"Connect through intellect — the next-gen social app where logic beats noise."

- **利用規約 / プライバシーポリシーURL**: GitHub Pages（リポジトリ `docs/` フォルダをソースに設定）でホスティングする。

- **データセーフティフォーム**: 収集データ（メールアドレス、投稿内容、広告ID、クイズ回答ログ等）を正確に申告。

### ランディングページ（GitHub Pages）

利用規約・プライバシーポリシーと同じGitHub Pages配信（`docs/`フォルダ）上に、アプリの顔となる
ランディングページを併設する。追加のホスティング費用を発生させず（GitHub Pages無料枠）、
Play Store審査中〜公開後の告知先、SNS/プロフィールのバイオリンク、Apple Store申請時の
「マーケティングURL」としても流用できる一枚のURLを用意することが目的。

- **原稿/実装**: `docs/index.html`（静的HTML+CSS。ビルドツール不要で完結させる）
- **公開URL**: `https://minnya.github.io/chatapp-renga/`
- **構成**:
  - ヒーロー: ロゴ + キャッチコピー（英語既定、日本語は補足として併記可）+ ストアバッジ2種（Google Play / App Store）
  - プロダクト紹介: 仮スクリーンショット（`assets/store/screenshots/`）を転用した3〜4枚のイメージと、Influence/Intellectの2軸評価・ロジックチェックといった主要機能の簡潔な訴求
  - フッター: 利用規約（`terms.html`）・プライバシーポリシー（`privacy.html`）・サポート連絡先へのリンク
- **ストアバッジのリンク先**:
  - Google Play: 公式バッジ画像（Google Play Badge Generatorで取得）をPlay Store公開後の実際のアプリURLへリンク
  - App Store: 公式"Download on the App Store"バッジを用意しておくが、Phase 1はAndroid先行リリースのため、iOS版審査提出（Phase 2、[8章 MVPスコープ定義](#8-mvpスコープ定義フェーズ分割)参照）が完了するまでは「Coming soon」表示または非活性リンクとし、公開後にURLを差し替える
- **デザインの一貫性**: 4章のデザインシステム（カラートークン・フォント）をそのまま踏襲し、アプリ本体との統一感を持たせる。
- GitHub Pagesの有効化手順自体は利用規約/プライバシーポリシーと共通のため [system.md — 11.6 GitHub Pages セットアップ](system.md#116-github-pages-セットアップ利用規約プライバシーポリシーランディングページ公開) を参照。

### リリースビルド運用

- `flutter build appbundle --flavor prod -t lib/main_prod.dart` でAndroid App Bundle（.aab）を生成し、Play Consoleにアップロード。
- 署名鍵（アップロードキー）は安全に管理し、Play App Signingを有効化する。
- バージョニングは `pubspec.yaml` の `version: x.y.z+build` をCIで自動インクリメントする運用を推奨。

## 8. MVPスコープ定義（フェーズ分割）

### Phase 1（MVP）

- Auth、Profile、通常投稿・フィード表示
- 画像投稿（Supabase Storage）、動画投稿（Mux直接アップロード・HLS配信）、YouTubeリンクの自動埋め込みプレビュー
- Android側のYouTube共有シート連携（YouTubeアプリの共有先にRengaを表示、Compose画面への自動プリフィル）
- オンボーディング3問クイズ、デイリーミッション3問（実装時にまず**手動で10問**の初期問題セットを用意し、それを土台にGemini自動生成パイプラインを段階的に稼働させる）
- 上位25%知能バッジ表示、レイヤーフィルター（全ユーザー/上位25%/上位5%）
- ステーキング投稿 + ロック解除クイズ
- Firebase基盤導入（FCMトークン登録・基本プッシュ通知、Remote Configによる基本フラグ、Crashlytics/Analytics導入）
- AdMob広告導入（ネイティブ広告のフィード差し込み）
- 多言語対応の土台（英語デフォルト + 日本語整備）
- アプリアイコン・ストア掲載情報（英語既定＋日本語訳）・スクリーンショット制作、Play Storeへの初回リリース

### Phase 2

- ロジックチェック（バトル）機能、観客ベット
- Endorse機能（logic_endorseによるバックアップ昇格）
- リポスト時警告フロー
- インタースティシャル広告の追加
- iOS側のYouTube共有シート連携（Share Extensionのネイティブ実装、App Groups経由での連携）

### Phase 3

- AI自動専門家発掘（Gemini APIによるドメインラベリング、専門家バッジ）
- クイズ自動生成パイプラインのフル運用（Generator/Solver/Validatorの3段階、人間レビューキュー）
- 3ストライク・累積ペナルティ、異議申し立てフロー
- 不正検知（回答時間分析によるAIチート検知）

### Phase 4（将来拡張）

- 限定チャット（音声ディベート形式）
- 収益分配機能
- IRTベースの高度なIntellectスコアリングモデルへの移行
- 英語・日本語以外の言語への展開
